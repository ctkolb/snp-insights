# SNP Insights

Turn a raw consumer DNA file into readable, **traceable** genetic findings —
without handing your genome to a language model.

SNP Insights parses your raw AncestryDNA file locally, annotates a curated set of
variants against public reference data, and computes every coverage state and
confidence value deterministically. A language model narrates the result — by
default a **local** model, so nothing leaves your machine. Every sentence it
writes is mechanically checked against the structured findings before anything is
rendered.

> **Not medical advice.** This is a research and curiosity tool. It is not a
> diagnostic test, a clinical-grade genetic test, or a substitute for a
> qualified clinician or genetic counselor. See [DESIGN.md](DESIGN.md).

## Pick your path

Three ways to use this repository. Start with Path A if you have never run it.

- **Path A: try it on synthetic data.** Needs Python and this repository. No
  personal file, no network, about two minutes. Go to
  [Quickstart A](#a-try-it-on-synthetic-data); the long version is
  [docs/getting-started.md](docs/getting-started.md).
- **Path B: run your own AncestryDNA file with the shipped release panel.**
  Needs your raw file and a private directory outside the repository. Private, no
  network, template report. Go to [Quickstart B](#b-run-your-own-file) and
  [docs/getting-started.md](docs/getting-started.md).
- **Path C: rebuild or extend the panel from public reference data.** Needs the
  network or large downloads (up to about 90 GB for the full files). Optional, for
  contributors. Go to [docs/reference-data.md](docs/reference-data.md).

## Quickstart

### A. Try it on synthetic data

Clone the repository with git and change into it; every command below runs from
there. Check that you have Python 3.12 or newer (`python3 --version`), then make a
clean environment. `jsonschema` is optional; it only turns on extra schema checks:

```bash
python -m venv .venv && source .venv/bin/activate
pip install jsonschema
python -m snp_insights --version
```

The version command prints `snp-insights 0.1.0`. Now run the whole pipeline on the
synthetic fixture, with no model and no network. Put the output **outside** the
checkout (a temporary directory is fine) so `run` has nothing to warn about:

```bash
OUT=$(mktemp -d)
python -m snp_insights run fixtures/raw.release.synthetic.txt data/targets.release-panel.json \
    --out-dir "$OUT/report" --template-only
```

It writes four files into `$OUT/report`: `findings.json` (the structured
findings), `report.md` (the report you read), `report.ir.json` (the report's
structure) and `report.run.json` (an audit record). The fixture is **synthetic**:
its genotypes are invented, so the report describes synthetic genotypes and says
nothing about you. A piece of the report:

```report
> This report was generated by fixed templates on this machine from structured findings; no language model was used to write it. It is a research and curiosity tool, not medical advice or a diagnostic test.
...
## Summary
...
- three curated markers were examined: three were measured, zero were not measured, and zero returned no call or an uninterpretable result. [f_065a9790e8ec · state] [f_b7dae4647a6b · state] [f_bfc3a4f653bb · state]
```

`python -m snp_insights <command>` works when the repository is the current
directory or on `PYTHONPATH`. `pip install -e .` also installs a `snp-insights`
console script; the test suite does **not** exercise that script (not verified
here). Installing a wheel outside the repository is **not supported**: the
sub-tools live in `tools/`, `stage2/` and `stage3/` outside the package, so the CLI
locates them relative to its own position in the repo. How to read the report, a
glossary and troubleshooting are in [docs/getting-started.md](docs/getting-started.md).

### B. Run your own file

1. **Get your raw file.** In your Ancestry account, open your DNA test's Settings
   and choose the DNA data download. The file arrives as a zip that contains a
   `.txt` file. Save and unzip it in a private directory **outside** the
   repository; never unzip it into the checkout. Details:
   [docs/getting-started.md](docs/getting-started.md#getting-your-raw-file).
2. **You do not need to fetch or build any reference data for v0.1.0.**
   `data/targets.release-panel.json` is already in the repository.
3. **Run the two private commands** in the next section, which also holds the rule
   for where to keep your files.

## Release panel and your own file

v0.1.0 ships a small public panel of three health-related entries and no trait
entries, built reproducibly from public references. The curation record is
[docs/panel-curation.md](docs/panel-curation.md), the curated evidence file is
`data/targets.release-evidence.json`, and the built panel is
`data/targets.release-panel.json`.

To check and run your own file, use these two commands. `$PRIV` stands for your
private directory (see the rule below). Name the release panel explicitly:
`check-raw` defaults to the sample panel.

```bash
python -m snp_insights check-raw "$PRIV/raw.txt" --panel data/targets.release-panel.json --no-hash
python -m snp_insights run "$PRIV/raw.txt" data/targets.release-panel.json --out-dir "$PRIV/out" --template-only
```

The first command inspects the file offline, with alleles redacted and no file
hash. The second runs the pipeline with no model and no network and writes the
report into `--out-dir`. The step-by-step procedure, including what to keep to
yourself, is [docs/owner-checkpoint.md](docs/owner-checkpoint.md).

**Where to keep your files.** Keep the raw file and all outputs in a private
directory outside the repository, any shared or synced folder, and any directory
an agent tool can read. `run` warns when `--out-dir` is inside the checkout but
cannot see other locations (a synced folder, or a directory mounted into another
tool), so keeping to this rule is up to you.

### What the report says

The template-only report states what was examined, how many markers were
measured, what each call state means (not measured means no information, not
absence), the evidence tiers with their source, and the limitations. It never
gives a diagnosis or a personal risk estimate.

## Why

Consumer DNA files contain real, interesting information that the vendors never
interpret. Re-reading that file is *interpretation*, not new lab work — but
generative interpretation is exactly where hallucination sneaks in: invented
confidence percentages, "the gene is absent" for a marker that was never
measured, and 1-star evidence dressed up as certainty.

SNP Insights is built so those failure modes are **structurally impossible**
rather than discouraged.

## How it works

```
Stage 1  Ingest    (local)   raw AncestryDNA .txt  ─┐
Stage 2  Annotate  (local)   snapshot panel + raw  ─┴─▶ findings.json
                                                         │
                                      ── privacy boundary ──
                                                         │
Stage 3  Narrate   (local)   findings.json ─▶ [LLM] ─▶ report_ir.json
                                              │
                                       validator (the harness enforces 7 rules)
                                              ▼
                                        renderer ─▶ report.md
```

- **Stages 1–2 are fully local.** Raw DNA never leaves the machine.
- **Stage 3 is local by default.** An online model is opt-in only, behind an
  explicit risk-acknowledgment flag.
- **The model authors prose only.** Numbers, caveats, citations, and
  contradictions are owned by code.
- **Every claim cites a `finding_id` + `field_path`.** If it isn't in
  `findings.json`, it can't reach the report.
- **Links are code-generated.** Each finding points to dbSNP, ClinVar, gnomAD,
  OMIM, SNPedia, MedlinePlus, and GeneReviews so you can read more — the model
  never writes URLs.

## Requirements

- Python 3.12 or 3.14 (the CI matrix); other 3.12+ versions are expected to work.
- `jsonschema` (optional) — enables JSON Schema validation passes. The semantic
  rule checks are pure standard library.
- [Ollama](https://ollama.com) (optional) — required only for Stage 3 with a
  local model, which is the default. Any OpenAI-compatible endpoint also works.

## Command reference

`python -m snp_insights --help` lists the six subcommands: `fetch`, `build-panel`,
`check-raw`, `annotate`, `narrate` and `run`. Each forwards the arguments after the
subcommand to the matching tool verbatim; `snp-insights <sub> --help` prints that
tool's own help (for `run`, its own usage).

**Annotate** (Stage 2, local): `python -m snp_insights annotate RAW PANEL -o findings.json`.

**Narrate** (Stage 3) runs a **local** model by default, so nothing leaves the
machine. Add `--template-only` to skip the model and stay fully offline:

```bash
python -m snp_insights narrate findings.json --model qwen2.5:14b -o report.md
python -m snp_insights narrate findings.json --template-only -o report.md
```

`--mode skeleton` (default) has code own the structure, citations, caveats and
contradiction text, and the model writes one sentence per claim. `--mode full` has
the model author the whole report IR (higher ceiling, more failure modes). The
model's output is validated and re-prompted with the violations (up to `--attempts`,
default 3); if it still fails, a deterministic template report is rendered.

An **online** model is opt-in and refuses to run without an explicit
acknowledgment flag, printing what would be sent and exiting with code 2:

```bash
python -m snp_insights narrate findings.json --endpoint openrouter \
    --model qwen/qwen-... --accept-privacy-risk -o report.md
```

> **Privacy.** An online model cannot be private: the derived findings, which are
> health-relevant, must be transmitted and may be retained by the provider. The
> online path withholds raw alleles and the file fingerprint and routes only to
> zero-retention providers, but that is risk *reduction*, not privacy. Only the
> local (default) or template paths keep findings on your machine.

**Run** (`run RAW PANEL`) annotates, then narrates, into `--out-dir` (default
`./snp-insights-out`):

- It **never overwrites** existing output without `--force` (exit code 1, nothing
  written), and refuses an output file that is a symlink or an `--out-dir` that is
  a file even with `--force`. A symlink used as `--out-dir` that points to a
  directory is not refused: `run` follows it, so use a normal private directory.
- `-o` and `--out` are refused (exit code 2). Every other option is forwarded to
  `narrate`, and everything after a `--` token is forwarded as is.
- Files it creates are mode `0600` and a directory it creates is `0700`. It prints
  a reminder that `findings.json` is private health data.
- The online gate is untouched: `run ... --endpoint openrouter` without
  `--accept-privacy-risk` exits with code 2 and makes no HTTP call.

**Check your file** with `python -m snp_insights check-raw RAW --panel PANEL`. It
parses the file with the same code as the pipeline and self-checks the format,
chromosome labels, no-call rate, allele alphabet, duplicate IDs, inferred sex and
the curated panel. By default it reports panel states only and withholds the raw
allele letters (`--no-redact` shows them), prints only aggregate counts, and
makes no network call. `--no-hash` omits the file fingerprint; `--json -o FILE`
writes machine-readable output. It defaults to the sample panel, so pass `--panel`.

Each subcommand wraps a script that also runs directly: `tools/fetch_reference.py`,
`tools/build_panel.py`, `scripts/check_raw.py`, `stage2/annotate.py` and
`stage3/run.py`. The CLI adds the sub-tools' directories to `sys.path` at call time
and refuses to load a sub-tool whose module resolves outside the repository.

### Optional: validate, render and score narrators

```bash
python tools/validate_report.py findings.json report_ir.json
python tools/render_report.py  findings.json report_ir.json -o report.md
```

The narrator harness scores model candidates against the findings (optional):

```bash
python tools/harness.py --findings fixtures/findings.sample.json \
    --config harness/candidates.json -o scorecard.md
python tools/harness.py --findings fixtures/findings.sample.json --live
```

The first uses stored candidate outputs, offline. The second uses a local Ollama
by default; Ollama (`http://localhost:11434/v1`) and OpenRouter
(`https://openrouter.ai/api/v1`) are preconfigured, and OpenRouter model IDs
(for example `qwen/qwen-...`) need `OPENROUTER_API_KEY`.

## Reference data

Annotation never touches the network. Reference data (dbSNP, ClinVar, gnomAD, the
GWAS Catalog, and optionally SNPedia) is fetched by a separate, explicit `fetch`
step into a local cache outside the repository. For v0.1.0 you do not need it.
[docs/reference-data.md](docs/reference-data.md) explains what each source is,
small fetch versus `--full`, the cache, the `build-panel` flags, the manual
downloads and the SNPedia path.

## Known limitations (v0.1.0)

- The array covers about 0.02% of the genome.
- Array presence of each marker is not verified: no public array manifest is
  available, so a marker may not be on your array version.
- The release panel has three health entries and no trait entries.
- The panel is small and public: it is a reproducible starting point, not a
  screening panel.
- Only template-only narration is verified in this release; the skeleton and full
  model modes and the online path were not exercised against a live model.
- A rare array call needs confirmation by a clinical-grade test.
- An input file with no build statement is annotated against GRCh37 and the report
  says so.
- X-linked and mitochondrial markers are excluded from the release panel (it is
  autosomal only).
- The first real-file run is the owner's local checkpoint and is not independently
  verified.

Accepted limits are recorded in [docs/accepted-limits.md](docs/accepted-limits.md).

## Design rules

The pipeline enforces seven hard rules in code (no invented numbers, three-state
reporting, evidence grades preserved, informational-not-prescriptive language,
contradictions flagged, standing caveats, and full claim traceability). See
[DESIGN.md](DESIGN.md#2-the-hard-rules-and-how-they-are-enforced) for the full
table and the enforcement mechanism.

## Testing

No dependencies required:

```bash
python tests/test_pipeline.py
```

`tests/test_pipeline.py` covers the parser, annotator, ETL, semantic lints and an
end-to-end validator accept/reject, and it calls the suites below. The evidence and
category suites are `tests/test_evidence.py` and `tests/test_category.py`. The CLI
and the privacy guard are `tests/test_cli.py` and `tests/test_guard.py`. The release
suites are `tests/test_release_panel.py` (the panel record and its data),
`tests/test_interpretation.py` (call interpretation),
`tests/test_report_readability.py` (the template report) and
`tests/test_docs_release.py` (this README, the two guides, AGENTS.md and the
accepted-limits register). `tests/test_result_block.py` checks the build-loop
result-block validator and runs separately.

Installing the optional `jsonschema` package (the `schema` extra) enables the
schema-validation passes; the suite runs without it. Each file also runs
standalone, e.g. `python -B tests/test_release_panel.py` and
`python -B tests/test_report_readability.py`.

## Privacy & safety

- **Never stored or sent:** the raw DNA file, parsed genotypes, `findings.json`,
  and any `panel.*.json` built from a real file are never transmitted and never
  committed. Annotation (Stage 2) is offline; the default narrator (Stage 3) is
  a local model. Only the opt-in online endpoint transmits derived findings, and
  it withholds raw alleles and the file fingerprint.
- **Never committed:** credentials, local config, home paths, generated panels,
  and owner-specific terms — enforced by a deny-by-default `.gitignore`, a
  tracked-file allowlist, and `scripts/guard.py`. CI runs the guard and a
  full-history secret scan; committed hooks mirror them locally.

```bash
git config core.hooksPath hooks     # enable the committed hooks (once)
python scripts/guard.py --full      # privacy/publication guard
```

See [docs/security.md](docs/security.md) for the threat model and control
inventory, and [SECURITY.md](SECURITY.md) to report an issue.
